# 세부조정 메뉴 재분석

아래는 개선 전 검토 기록이다. 구현 결과는 [세부조정 개선](fine-tune-improvements.md)을 참고한다.

2026-09-13. 원격 `main`과 일치하는 `d05592c` 기준. 세부조정은 배틀 전에 내 포켓몬의 능력 포인트를 조정하고 그 결과를 비교하는 메뉴로 검토했다. 제품 소스는 변경하지 않았다.

## 판단

현재 메뉴는 수동 배분표로 가치가 있다. 각 능력치 0~32, 총합 66 제한, 성격별 실수치, 성격 보정 효율 구간, HP 기준점, 최속·준속·무보정 상대의 추월선이 연결돼 있다. 다만 계산기와 왕복하며 배치를 완성하는 과정에는 조건 유실과 상대 배치 초기화 문제가 있어, 현 상태를 완성된 조정 도구로 보기는 어렵다.

이 메뉴의 중심은 **배분 변경 전후 무엇을 얻고 무엇을 잃는지**다. 스피드 목표에 필요한 포인트, HP 회복·소모의 실제 차이, 물리·특수 내구 변화와 남은 포인트를 함께 보여 주는 방향이 적합하다.

역계산에서 합의한 H32 우선은 상대 후보를 정하는 가정이다. 이를 세부조정의 강제 배분 규칙으로 옮기면 사용자가 직접 정하는 스피드·HP 조건과 충돌한다. 세부조정에서는 H32를 비교 기준으로 활용할 수 있지만 실제 배분은 자유롭게 조정할 수 있어야 한다.

## 1. 계산기 왕복 시 조건과 상대 배치 보존 — 우선 수정

침바루의 쓱쓱을 활성화하면 세부조정 스피드는 210이다. 이를 계산기로 보내면 날씨는 `none`이고 스피드는 105가 된다. 비 상태의 계산기에서 세부조정으로 불러오는 반대 방향도 210에서 105가 된다.

더 큰 문제는 상대 배치 초기화다. 계산기에 설정한 한카리아스 H32/B32/D2, 장난꾸러기, 먹다남은음식, 지진을 두고 내 포켓몬의 S만 조정해 되돌렸을 때, 상대가 무투자·무보정·도구 없음·기술 없음으로 바뀐다. 조정 전후의 대미지를 같은 상대 조건으로 비교할 수 없다.

필요한 변경:

- 양쪽 배치와 공통 필드 조건을 보존한다. 내 쪽 배분 적용 때문에 계산기의 상대 설정을 새 기본값으로 만들지 않는다.
- 특성 체크를 별도 가상 상태로 유지하는 대신 계산에 사용하는 날씨·필드·상태를 명시하고 전달한다.
- 기존 배치를 불러올 때와 새 포켓몬을 고를 때의 상태 초기화 범위를 구분한다.

근거: `src/js/04-31-finetune-render.js`의 `ftApplyToCalc`, `loadSideToFineTune`; `src/js/04-30-finetune.js`의 `ftDefaultField`, `ftSpeedFieldFor`.

## 2. 양쪽 스피드 조건과 필요 투자 표시 — 우선 수정

내 스피드는 공통 엔진을 사용하지만 상대는 종족값·성격·포인트·랭크·스카프만 계산한다. 상대 침바루 준속은 137로 표시되며, 동일한 배치를 공통 엔진의 비/쓱쓱 조건으로 계산하면 274다. 상대 특성·날씨·필드·마비·순풍 등을 같은 기준으로 비교할 수 없다.

불러온 내 상태에도 표시 문제가 있다. 마비된 포켓몬을 불러온 뒤 한카리아스로 교체하면 마비가 남아 스피드는 61이지만, 요약은 ‘추가 보정 없음’이다. 실제로 적용한 조건을 모두 보여 주고, 새 배치에 남길 조건을 명확히 해야 한다.

현재 ‘불가’는 두 경우를 섞는다. 한카리아스 H32/A32에서는 S에 2만 남아 상대 최속 침바루 추월 목표 151을 만족하지 못한다. 그러나 다른 축을 줄이면 S29로 달성 가능하다. 실제 포인트 조정 도구는 이 차이를 보여 줘야 한다.

필요한 변경:

- 상대도 공통 스피드 엔진과 동일한 조건을 사용한다.
- ‘최소 S29 / 현재 여유 2 / 다른 능력치에서 27 필요’처럼 표시한다.
- 현재 배분 부족, S32 내 달성 불가, 현재 달성 상태를 구분한다.
- 입력 0이 내부에서 1로 바뀌는 추월 마진 처리를 정리한다. 동속 허용을 지원하거나, 추월 전용이면 최소 1로 입력을 제한한다.
- ‘속도’ 입력이 실제로는 종족값이라는 점을 이름에 드러낸다. 최속·준속·무보정 비교와 사용자가 지정한 상대 실수치 목표를 구분한다.

근거: `src/js/04-30-finetune.js`의 `ftOppSpeedCase`, `ftFindMinSpeedEv`, `ftBuildSpeedTable`, `ftApplyPokemonToFineTune`; `src/js/04-31-finetune-render.js`의 `renderFineTuneSpeed`.

## 3. HP 기준점을 선택한 배치의 실제 이득으로 연결 — 필수 보완

현재 HP 패널은 16n, 16n±1, 8n±1 등의 조건에 맞는 이전·다음 투자량을 보여 준다. 하지만 회복량·소모량과 조정 후 HP가 없어, 사용자가 해당 조건을 위해 포인트를 옮길 가치가 있는지 판단하기 어렵다.

자뭉열매를 선택해도 반피 발동선과 회복량에 대한 전용 기준이 없다. 매직가드 픽시에도 스텔스록·압정·도트 관련 기준이 관련 항목으로 남는다. 특성·타입·도구 때문에 해당하지 않는 기준과 실제로 고려할 기준의 구분이 부족하다.

필요한 변경:

- 도구와 특성에 맞는 항목을 우선 표시한다. 미적용 기준은 일반 참고로 구분한다.
- 현재 HP → 조정 후 HP, 필요한 포인트, 회복·소모량의 실제 변화를 보여 준다.
- 자뭉열매 등의 발동 HP와 회복량을 추가한다. 16n 등 특정 나머지 조건을 무조건 최적 배분으로 표현하지 않는다.
- ‘+1턴’ 설명은 해당 비율의 소모만 반복되고 다른 피해·회복이 없는 조건임을 명확히 한다.

대조 자료: 저장소의 `data/items.ts` 및 `data/overrides/item-mechanics.json`에 자뭉열매의 반피 발동과 최대 HP의 1/4 회복이 있다. `data/abilities.ts`의 `magicguard`는 기술 외 피해를 차단한다.

근거: `src/js/04-30-finetune.js`의 `ftHpBreakpointRules`, `ftHpBreakpointDeltas`; `src/js/04-31-finetune-render.js`의 `renderFineTuneHp`.

## 4. 배분 전후 비교와 적용 — 사용성 보완

현재 물리·특수 내구는 `HP × 방어 또는 특방 / 0.411` 값이다. 배분 효율 비교에는 쓸 수 있지만 상대 기술, 특성·도구의 직접 피해 보정이나 생존 결과를 뜻하지 않는다. 랭크를 바꿔도 이 값은 그대로다. 무엇을 포함한 지표인지 표시해야 한다.

권장 변경:

- 기준 배분 하나를 저장하고 현재 배분의 실수치·내구 지표·속도·남은 포인트 차이를 보여 준다.
- 필요 S와 HP 기준점에 적용 버튼을 둔다. 총합이 넘는 경우 부족량을 표시하고, 다른 능력치에서 포인트를 자동으로 빼지 않는다.
- 초기 배분 복원과 계산기 적용을 분명히 구분한다.
- 기존 파티 불러오기와 계산기 전달을 유지한다.

## 후속 확장 범위

특정 상대에 대한 확정 KO, 특정 기술 생존을 조정 전후로 비교하면 대전 준비 도구로서 가치가 더 높아진다. 우선은 기존 대미지 계산기와 조건이 유지되는 왕복, 또는 선택한 기술 한두 개의 비교로 충분하다. 여러 상대의 공격·생존·속도 목표를 동시에 만족시키는 자동 배분 탐색은 별도 확장으로 구분한다.

완료 기준은 배틀 전체 재현이 아니다. 사용자가 ‘무엇을 추월하려고 S를 얼마 투자했고, 그 대신 HP와 내구를 얼마나 조정했는지’를 동일한 조건으로 확인할 수 있어야 한다.

- 기존 세부조정 상태 검사 37개 통과.
- `node scripts/fine-tune-menu-review.mjs`에서 현재 동작 9개를 재현했다. 결과는 `fine-tune-menu-review-probes.json`에 기록했다.
- 진단 스크립트는 DOM 그리기만 대체하고 실제 상태 전달·스피드·HP 기준점 함수를 호출한다. 버그 재현과 기능 부재 확인을 위한 것이며 수정 후 통과해야 할 회귀 테스트는 아니다.
- 이번 평가는 현재 HTML·CSS·JS 구조와 계산 동작을 기준으로 한다. 새 브라우저 시각·접근성 검사는 실행하지 않았다.
- 우선순위는 **조건과 배치 보존 → 양쪽 스피드와 필요 포인트 → HP 기준점 → 변경 전후 비교**다.
