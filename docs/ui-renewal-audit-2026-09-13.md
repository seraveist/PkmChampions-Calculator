# 전체 메뉴 UI 개편 사전 점검

2026-09-13. 계산기·형태 역계산·세부조정·도감·상성표의 최근 로컬 개선이 모두 반영된 상태를 기준으로 한다. 기존 기본 컨셉, 밝은/어두운 테마, 공격·방어 및 타입 색상은 유지한다.

## 결론

공통 입력과 화면 계층을 다시 설계하고 각 메뉴를 그 기준으로 옮기는 개편이 적절하다. 현재 기능은 갖춰져 있으나, 입력과 결과의 거리, 동일한 역할을 하는 컨트롤의 차이, 반복되는 테두리와 작은 글씨 때문에 활용도가 낮아진다. 개별 CSS 수치만 추가로 덮어쓰면 같은 문제가 재발하기 쉽다.

우선순위는 **공통 구조 → 계산기 → 세부조정 → 형태 역계산 → 상성표 → 도감·공통 팝업**이다. 계산기로 공통 편집기를 검증하고, 세부조정에서 가장 긴 입력/결과 흐름을 줄인 뒤 나머지 메뉴에 적용한다. 도감의 제목 크기처럼 독립적인 표시 결함은 앞 단계에서도 함께 수정할 수 있다.

## 확인 범위와 한계

- 실제 공개용 로컬 빌드에서 5개 메뉴를 1440 / 1024 / 768 / 375 / 320px로 확인했다.
- 계산기 상세 펼침, 상성표 타점 체크를 포함해 29개 화면 상태의 배치를 측정했다. 결과 영역, 도감 상세, 빈 파티 프리셋 팝업도 캡처해 확인했다.
- 역계산은 예시 한 턴 관측을 실제 계산한 결과를 사용했다. 계산기와 세부조정은 예시 배치를 입력했다. 길이 수치는 이 예시의 결과이며 모든 조합의 고정값이 아니다.
- 5개 메뉴의 밝은/어두운 테마에서 자동 접근성 검사 위반 및 실행 예외는 검출되지 않았다. 문서 전체 가로 넘침도 측정한 29개 상태에서 0px였다.
- HTML 구조·CSS 구조·CSS cascade 검사도 통과했다. 이는 시각적 계층, 읽기 쉬운 제목, 결과까지의 거리, 모든 동적 상태까지 검증됐다는 뜻은 아니다.
- 실제 사용자의 개인 파티 저장 데이터, 모든 긴 설명·폼·후보 조합, 모든 팝업의 편집/오류 상태를 전수 검사한 것은 아니다. 새 UI 구현 시 아래 완료 기준으로 추가 검증한다.

## 우선 해결할 공통 문제

### 1. 결과와 실제 작업 영역이 너무 멀다 — 높음

375px 화면에서 문서 상단을 기준으로 측정했다. 화면 높이는 900px, 고정 헤더 높이는 94px다.

| 메뉴·상태 | 주요 영역 시작 | 전체 문서 높이 | 영향 |
| --- | ---: | ---: | --- |
| 계산기 기본 | 결과 2,650px | 4,278px | 상대 설정과 기술 비교를 왕복해야 한다. 기존 하단 요약은 도움이 되지만 전체 비교는 멀다. |
| 계산기 상세 펼침 | 결과 4,221px | 5,849px | 상세 입력이 모두 앞에 놓여 결과와 더욱 멀어진다. |
| 형태 역계산 | 결과 3,355px | 5,648px | 한 턴 관측 전에 내 배치와 상대 랭크 편집이 길게 이어진다. |
| 세부조정 | 상대·스피드 4,386px | 6,592px | HP 기준점 목록을 지나야 추월 목표를 편집할 수 있다. |
| 상성표 방어 | 표 1,018px | 2,092px | 여섯 슬롯이 표보다 먼저 모두 펼쳐진다. |
| 상성표 타점 | 표 2,680px | 3,799px | 포켓몬 설정과 기술 설정을 별도 카드로 반복한다. |
| 도감 목록 | 목록 345px | 9,585px | 목록은 빨리 나오지만 각 포켓몬의 정보를 큰 카드로 전부 펼쳐 탐색이 길어진다. |

세부조정은 데스크톱에서도 `editor hp / speed speed` 배치이므로, 긴 HP 패널이 끝난 뒤에 상대·스피드가 시작한다. 1440px 예시에서도 해당 영역은 1,892px 아래다. [레이아웃 근거](../src/styles/pages/02-finetune.css#L146)

개편 방향: 자주 바꾸는 입력과 결과를 같은 작업 영역에 배치하고, 기본 상태에서는 핵심 입력만 보인다. 상세 설정은 현재 값 요약이 있는 접힘 영역으로 옮긴다. 이미 있는 값을 숨겼다는 이유로 초기화하거나 계산에서 제외하지 않는다.

### 2. 테두리와 제목의 단계가 의미를 구분하지 못한다 — 높음

예시 화면의 `.ui-frame / .ui-control-frame / .ui-subframe / .panel`은 계산기 23개, 역계산 33개, 세부조정 18개다. 주요 도구 메뉴는 이 컨테이너가 최대 3단계 중첩된다. 일반 입력 묶음, 보조 설명, 최종 결과가 유사한 배경·테두리·굵은 제목을 사용한다.

- 큰 영역은 패널, 그 안의 일반 묶음은 제목·여백·구분선으로 나눈다.
- 결과 카드나 별도 조작이 필요한 작은 묶음에만 추가 테두리를 사용한다.
- 큰 제목 / 영역 제목 / 입력 라벨 / 보조 설명 / 결과 수치의 크기와 굵기를 분리한다.
- 한 영역의 대표 버튼을 하나로 정하고 나머지는 보조 액션으로 둔다. 계산기의 결과 영역에서 현재 가장 강한 버튼이 `공수교대`인 것도 재정리 대상이다.

### 3. 같은 입력의 형태와 조작 크기가 다르다 — 높음

- 계산기는 특성·도구·성격·상태를 한 방식으로, 세부조정·역계산은 별도 다중 클래스와 다른 순서로 배치한다.
- 계산기/내 배치의 성격·특성은 검색형 입력인데, 일부 상대 설정 및 상성표는 기본 선택창이다. 모두 검색형으로 강제하기보다, 검색이 필요한 긴 목록과 작은 고정 선택지를 구분해 공통 부품으로 만든다.
- 모바일 역계산의 상대 랭크 `+/-`는 22×22px, 계산기 위력 자동 복원은 높이 24px, 도감 타입 필터는 28px다. 자동 접근성 검사 통과와 별개로 손가락으로 반복 조작하기에는 크기가 제각각이다.
- 내보내기/메뉴 이동 버튼도 `공격측`, `방어측`, `세부조정`, `역계산` 등 현재 위치에 따라 의미를 추측해야 한다. 적용·이동 동사를 포함해 역할을 명확히 한다.

개편 방향: 포켓몬 선택, 특성·성격·도구 묶음, 포인트·랭크 편집, 기술 선택, 선택 탭, 접힘 영역, 적용 버튼을 공통화한다. 기본 조작 높이는 모바일 40~44px 중심으로 맞추고, 숫자 증감도 실제 터치 영역을 확보한다. 이는 제품 설계 목표이며 현재 전부 접근성 기준 위반이라는 판정은 아니다.

### 4. 도감 제목 크기와 실제 HTML 제목 계층이 어긋난다 — 높음

도감 상세의 포켓몬 이름은 모든 폭에서 44px / 줄높이 44px로 고정된다. 375px에서 `한카리아스`는 두 줄, 320px에서 `블레이범 (히스이)`는 세 줄(132px)이 된다. 글자 크기만을 위한 기존 모바일 `.dex-fullpage-title` 규칙은 실제 이름 `.dex-detail-name > b`에 적용되지 않는다.

또한 확인한 포켓몬 상세 내부에는 `h1~h3`가 없다. 화면의 이름은 `<b>`, 영역 제목은 `<div>`여서 시각적으로는 제목이지만 문서 탐색 구조에 드러나지 않는다.

개편 방향: 상세 이름은 의미 있는 제목 요소로, 종족값·특성·학습 기술은 그 아래 제목 단계로 만든다. 모바일 이름은 22~28px 범위의 가변 크기, 이름과 폼 정보 분리, 단어 단위 줄바꿈으로 정리한다.

근거: [44px 이름 규칙](../src/styles/pages/dex-20-detail.css#L360), [실제 제목 마크업](../src/js/04-11-dex-detail.js#L211), [다른 클래스를 대상으로 한 모바일 규칙](../src/styles/pages/dex-40-responsive.css#L21).

### 5. 빈 공간이 내용과 상관없이 유지된다 — 중간

세부조정은 중립 성격처럼 매직넘버 안내가 없는 경우에도 `visibility: hidden`으로 해당 셀을 남긴다. 모바일에서는 내용 없는 셀이 각 능력치 카드에 높이 34px의 행을 차지한다. 실수치 자체는 정상적으로 표시되며, 문제는 비어 있는 보조 행을 항상 예약한다는 점이다.

개편 방향: 빈 조건부 안내는 해당 행 자체를 제거한다. 매직넘버가 있는 능력치에만 바로 아래 보조 정보를 표시한다. HP 기준점도 모두 같은 무게로 나열하지 않고 도구·선택한 목적에 관련된 것을 먼저 보여 주되, 전체 기준은 펼쳐 확인할 수 있게 한다.

근거: [빈 매직넘버 셀](../src/styles/pages/02-finetune.css#L451), [모바일 능력치 행 구성](../src/styles/responsive.css#L693).

### 6. 탐색 방식과 목록 밀도를 정리해야 한다 — 중간

- 320px에서 다섯 번째 주 메뉴의 오른쪽 끝은 약 344px로 화면 밖이다. 문서 넘침은 없지만 메뉴 자체에 가로 탐색이 필요하며, 경로로 메뉴를 열어도 선택한 탭이 전부 보인다고 보장되지 않는다.
- 도감의 모바일 포켓몬 카드는 종족값 6개와 특성별 행까지 기본으로 보여 주어 첫 페이지가 약 9,600px가 된다. 이름·타입·핵심 정보 중심의 목록과 상세 화면의 역할을 분리할 필요가 있다.
- 파티 팝업은 빈 저장 슬롯들도 많은 세로 공간과 가져오기/내보내기 버튼을 반복한다. 저장 파티 목록 → 선택한 파티 편집 → 공유/가져오기 액션으로 분리하는 편이 낫다. 이번 확인은 빈 프리셋 상태에 한정한다.

## CSS와 HTML 구조의 개편 기준

현재 37개 CSS 파일에 약 342KB, 1,953개 규칙, 미디어 쿼리 41개, 폭 기준 14종이 있다. 규모 자체를 결함으로 판정하지는 않지만, 같은 개념의 구현이 분산된 상태에서는 수정 영향 범위를 추적하기 어렵다.

1. **색상 원본은 유지하고 중복 별칭을 정리한다.** `00-tokens.css`의 제품 색상·타입 팔레트를 기준으로 삼는다. `.tool-page`에서 동일한 색을 다시 직접 선언하는 구조는 의미 토큰 참조로 옮긴다.
2. **페이지 파일은 해당 페이지 배치만 담당한다.** 세부조정 파일의 `.tool-page .tool-stat-grid`는 다른 도구 메뉴까지 영향을 준다. 이런 공유 규칙은 공통 능력치 편집기 파일로 이동해야 한다. 기존 검사에서 `Cross-page CSS ownership: none`으로 나오는 이유는 다른 `#page-*` 참조 중심의 검사여서 이 형태를 놓치기 때문이다.
3. **기본·변형·반응형 규칙의 담당을 분명히 한다.** 공통 모양은 부품 파일, 메뉴별 배치는 페이지 파일, 테마는 색상 변수로 분리한다. 같은 부품의 모바일 규칙이 여러 파일에서 연속으로 보정되지 않게 한다.
4. **좁은 화면은 별도 구성으로 설계한다.** 세부조정에는 430/380px 규칙 뒤 760px 규칙이 있고, 공용 `responsive.css`가 다시 카드 형태로 덮어쓴다. 이 경로를 단순화해 모바일·중간·넓은 화면 중심으로 정리한다. 새 UI를 검증하면서 불필요한 분기만 제거한다.
5. **겹치는 역할의 클래스 묶음을 줄인다.** 예를 들어 하나의 성격 입력에 `tool-settings-choice-*`, `tool-settings-select-*`, `ui-control-*`, `ft-*`를 모두 부여하는 대신 공통 입력 + 필요한 변형 + 페이지 배치로 나눈다.
6. **렌더링과 이벤트 연결을 함께 이전한다.** 입력 변경 때 영역 전체를 새로 만들면 포커스·드롭다운·접힘 상태가 흔들릴 수 있다. 상태가 살아 있는 입력은 가능한 한 유지하며, 기존 계산/파티 적용 함수를 연결한다.
7. **검사도 새 구조를 따라 바꾼다.** 현재 특정 클래스의 존재나 최대 높이를 지키는 검사를 그대로 UI 목표로 삼지 않는다. 의미 있는 값 표시, 입력값 보존, 결과 접근, 긴 이름 줄바꿈, 실제 터치/키보드 흐름을 검증한다.

| 계산기 | 양측 포켓몬·배치 요약, 내 기술 4개, 각 기술의 피해 범위·KO 정보 | 타입 수동 변경, 기술 위력 직접 수정, 방어측 기술 편집, 상세 랭크·추가 효과 | 넓은 화면은 입력과 결과를 나란히, 좁은 화면은 양측 요약 → 내 기술·결과 → 선택한 상세 편집 |
| 형태 역계산 | 조우 상대, 시작 HP 요약, 선후공·사용 기술·남은 HP·관측 도구 | 내 전체 배치 편집, 추가 관측과 특수 상태 | 참가자 요약 → 한 턴 관측 → 분석 → 다음 턴 상태·선후공·피해 비교 → 후보별 상세 |
| 세부조정 | 내 포인트 편집, 남은 포인트, 변경 전후 수치, 선택한 조정 목표 | 관련 없는 HP 기준점 전체 목록, 세부 랭크·필드 | 편집기 + 목표 영역. 목표는 스피드 / HP로 전환하고 전후 비교를 가까이 둠 |
| 상성표 | 6마리의 간단한 요약, 방어·타점 탭, 타입 표 | 선택한 포켓몬의 폼·특성·기술 편집 | 파티 요약 → 타입 표, 선택한 슬롯의 설정만 펼치기. 고정 상대 평가를 다시 만들지 않음 |
| 도감 | 검색·필터, 이름·타입 중심 목록, 상세의 기본 정보 | 각 목록 행의 모든 종족값·특성 설명 | 간결한 목록 → 상세. 학습 기술 필터 유지, 긴 이름과 폼의 모바일 표시 정리 |

기능 범위는 지금까지 합의한 것을 유지한다. 계산기는 결정력 비교 중심이며, 역계산은 한 턴 관측과 다음 턴 판단에 필요한 데이터 제공에 집중한다. UI 개편을 이유로 턴 전체 재현·자동 행동 추천·고정 상대 평가를 추가하지 않는다.

## 구현 순서와 완료 기준

1. 공통 패널·입력·숫자 편집·탭·접힘·결과 카드·헤더를 정의하고 계산기의 대표 배치를 먼저 만든다. 모바일을 데스크톱 축소판으로 처리하지 않는다.
2. 계산기 입력/결과를 연결하고, 기존 결정력 정책과 계산 결과가 바뀌지 않는지 확인한다.
3. 세부조정의 스피드·HP·비교를 재배치하고, 역계산의 관측 입력과 후보 비교를 동일한 공통 부품으로 옮긴다.
4. 상성표·도감·파티 팝업을 정리하고 대체된 HTML/CSS를 제거한다. 사용 중인 상태/이벤트를 확인하지 않고 클래스명 검색만으로 삭제하지 않는다.
5. 기본·입력 완료·상세 펼침·빈 결과·오류·다중 후보·긴 이름·팝업 상태를 검증한다.

완료 기준:

- 핵심 입력을 끝낸 뒤 주 결과가 기본 화면 또는 바로 다음 작업 영역에서 보인다. 긴 보조 목록을 지나야 핵심 입력이 나오는 구성을 없앤다.
- 메뉴별 입력 라벨·높이·포커스·적용/복원 동작이 같고, 현재 값은 접기·펼치기·메뉴 이동으로 사라지지 않는다.
- 모바일 포켓몬 이름이 불필요하게 한 글자씩 갈라지지 않고, 내용 없는 보조 행은 공간을 차지하지 않는다.
- 선택한 주 메뉴와 현재 작업 상태가 항상 식별 가능하다. 고정 영역이 입력·팝업·마지막 결과를 가리지 않는다.
- 320/375/768/1024/1440px, 양쪽 테마, 키보드·터치에서 확인한다. 표 내부 가로 스크롤과 문서 전체 넘침은 구분한다.
- 계산·역계산·파티 상태 회귀 검사와 새 UI의 실제 화면 검사를 모두 통과한다.

이번 작업은 점검 자료와 재현 스크립트를 추가한 단계다. 제품 HTML/CSS의 개편은 이 기준에 따라 후속 구현한다.
