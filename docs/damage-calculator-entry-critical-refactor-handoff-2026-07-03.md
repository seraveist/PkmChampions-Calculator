# 대미지 계산기 자동 진입 효과 및 급소 처리 리팩터링 핸드오프 - 2026-07-03

## 문서 목적

이 문서는 대미지 계산기의 자동 진입 효과, 확정 급소 기술, 기술별 수동 급소 설정을
다른 작업 환경에서 안전하게 구현하기 위한 핸드오프 문서다.

이 문서를 작성한 시점에는 실제 소스 수정이 적용되지 않았다. 현재 기준은 다음과 같다.

- 브랜치: `main`
- 기준 커밋: `29d351d chore: sync PS data 2026-06-28`
- 로컬과 `origin/main` 동기화 상태
- `npm.cmd test` 전체 통과
- 빌드 후 작업 트리 변경 없음

## 목표

1. 양쪽 포켓몬이 날씨 또는 필드 특성을 가질 때 마지막으로 조작한 선택칸의 효과를 적용한다.
2. 자동 효과를 만든 포켓몬을 교체하면 반대편 효과 또는 기존 수동값으로 안전하게 복원한다.
3. 위협, 자기 랭크 상승, 다운로드는 재계산 시 누적되지 않도록 파생 상태로 유지한다.
4. 재앙 특성은 진입 랭크 효과와 분리하여 상시 특성 효과로 취급한다.
5. 원본 기술 데이터의 `willCrit`을 빌드 결과와 공통 대미지 엔진에 전달한다.
6. 메인 계산기의 전역 급소 체크를 제거하고 네 기술 슬롯별로 급소를 설정한다.
7. 역계산과 세부조정의 기존 UI 계약은 유지하면서 공통 엔진 개선만 공유한다.

## 현재 확인된 구조

### 자동 진입 효과

`data/overrides/entry-effects.json`은 다음 효과를 한 객체에 정의한다.

- 날씨: 가뭄, 잔비, 모래날림, 눈퍼뜨리기, 진홍빛고동 등
- 필드: 일렉트릭메이커, 그래스메이커, 사이코메이커, 미스트메이커, 하드론엔진
- 자기 랭크: 불요의검, 불굴의방패, 초상투영
- 상대 랭크: 위협
- 조건부 랭크: 다운로드
- 상시 효과: 재앙 특성 4종

현재 `applyEntryEffectsToCalcState()`는 항상 `['atk', 'def']` 순서로 양쪽 효과를 적용한다.
따라서 양쪽 모두 날씨 특성이면 사용자가 마지막으로 수정한 쪽과 관계없이 방어측 날씨가
최종값이 된다.

위협과 다운로드 등은 원본 `state`를 직접 변경하지 않고 `makeCalcState()`의 계산용 복사본에
적용된다. 이 구조 덕분에 재계산할 때 랭크가 누적되지 않고, 특성을 제거하면 수동 랭크로
복원된다.

### 확정 급소 기술

원본 `data/moves.ts`의 트릭플라워에는 이미 다음 필드가 있다.

```js
willCrit: true
```

하지만 현재 `build.mjs`가 이 필드를 생성 기술 데이터에 보존하지 않는다. 생성 HTML의
`flowertrick` 데이터에는 설명만 있고 `willCrit`이 없다.

현재 엔진은 다음 경우만 급소로 판정한다.

- 메인 필드의 수동 `isCritical`
- 독 상태 대상에 대한 무자비 등 특성 조건

따라서 원본 데이터의 확정 급소 기술이 자동 급소로 계산되지 않는다.

원본 데이터에서 확인된 `willCrit: true` 기술은 다음과 같다.

- 트릭플라워 (`flowertrick`)
- 얼음숨결 (`frostbreath`)
- 업어후리기 (`stormthrow`, 현재 Past 필터로 빌드 제외)
- 수류연타 (`surgingstrikes`)
- 암흑강타 (`wickedblow`)

### 현재 급소 UI

메인 계산기의 급소 체크박스는 필드 패널에 있으며 `state.field.isCritical`을 변경한다.
공격측의 네 기술이 같은 필드를 공유하므로 체크하면 네 기술이 모두 급소로 계산된다.

급소는 전역 필드가 아니라 개별 기술 실행 결과이므로 기술 슬롯별 상태로 옮기는 것이 목표다.

## 목표 설계

### 1. 날씨 및 필드 자동 효과

날씨와 필드는 계산용 복사본에서 매번 고정 순서로 적용하지 않는다. 현재 자동 효과를 만든
선택칸과 자동 적용 전의 수동값만 최소 상태로 보관한다.

예시 구조:

```js
const autoEntryFieldState = {
  weather: { owner: null, base: 'none' },
  terrain: { owner: null, base: 'none' },
};
```

- `owner`: `'atk'`, `'def'`, `null` 중 하나
- `base`: 자동 효과가 없을 때 사용할 수동 또는 기본값
- `state.field.weather`와 `state.field.terrain`: 화면과 모든 계산 코드가 읽는 최종 적용값

전체 선택 이력을 저장할 필요는 없다. 현재 소유자와 복원값만 관리한다.

#### 필수 동작

| 입력 | 결과 |
| --- | --- |
| 공격측 가뭄 선택 | 쾌청, weather owner=`atk` |
| 이후 방어측 잔비 선택 | 비, weather owner=`def` |
| 비소유자 포켓몬 변경 | 현재 날씨 유지 |
| 소유자를 일반 포켓몬으로 변경 | 반대편 날씨 특성 또는 base 복원 |
| 양쪽이 같은 날씨 특성 | 표시값이 같아도 마지막 선택칸으로 owner 갱신 |
| 수동 날씨 선택 | owner 해제, 선택값을 새 base 및 최종값으로 지정 |
| 자동 효과 OFF | 최종값을 base로 복원하고 자동 필드 효과 비활성화 |
| OFF 상태에서 포켓몬 변경 | owner 후보는 현재 선택 상태에 맞게 갱신하되 화면에는 적용하지 않음 |
| 자동 효과 ON | 현재 유효한 owner가 있으면 다시 적용 |
| 공수교대 | owner의 `atk`와 `def`도 함께 교환 |
| 전체 초기화 | owner/base 초기화 후 양쪽 기본 특성을 결정적인 순서로 재평가 |

같은 값일 때 조기 반환하면 안 된다. 예를 들어 양쪽이 모두 쾌청을 만들더라도 마지막으로
선택한 쪽이 owner가 되어야 이후 교체 시 올바르게 복원된다.

#### 입력 경로

자동 필드 갱신 함수는 다음 경로에서 최종 포켓몬과 특성이 확정된 뒤 호출해야 한다.

- 메인 계산기 포켓몬 선택
- 메인 계산기 특성 변경
- 폼 변경
- 도감에서 공격측 또는 방어측으로 적용
- 파티 프리셋에서 계산기로 적용
- 전체 기본값 복원

프리셋은 특히 주의한다. 현재 `applyPokemonToCalcSide()`가 기본 특성을 설정한 뒤
`partyPresetApplyMemberToSideState()`가 저장된 특성으로 다시 덮어쓴다. 자동 효과 판정은 반드시
저장된 최종 특성이 적용된 다음 실행해야 한다.

#### 권장 함수 경계

```text
entryFieldEffectForSide(sideKey, fieldKey)
applyEntryFieldsFromSide(sideKey)
setManualCalcField(fieldKey, value)
setAutoEntryEffectsEnabled(enabled)
swapAutoEntryFieldOwners()
resetAutoEntryFieldState()
```

함수명은 기존 코드 스타일에 맞춰 조정할 수 있지만, DOM 이벤트가 직접 owner/base를 조작하지
않도록 한다.

### 2. 랭크 및 상시 효과

다음 효과는 입력 이벤트에서 원본 랭크를 직접 변경하지 않는다.

- 자기 랭크 상승
- 위협
- 다운로드

계산용 복사본에만 적용해야 다음 동작을 보장할 수 있다.

```text
수동 공격 랭크 0 + 위협  = 계산값 -1
위협 제거                 = 계산값 0

수동 공격 랭크 +2 + 위협 = 계산값 +1
위협 제거                 = 계산값 +2
```

권장 내부 분리:

```text
applyDerivedEntryRankEffects(calcState, meta)
applyContinuousAbilityEffects(calcState, meta)
```

재앙 특성은 랭크 진입 효과가 아니라 현재 특성 보유 여부에 따라 작동하는 상시 효과이므로 두 번째
함수에서 처리한다. 기존 수동 재앙 체크박스와 자동 효과 OFF 동작은 유지한다.

`entryMeta.rankDeltas`는 속도 랭크 표시 등에 사용되므로 유지한다. 로그와 차단 정보도 테스트 및
진단용으로 남기는 편이 안전하다.

이번 작업에서 모래뿜기의 실제 피격 발동 조건, 초상투영의 테라스탈 조건, 불요의검 및
불굴의방패의 배틀당 1회 조건은 변경하지 않는다. 별도 메커니즘 정합성 작업으로 분리한다.

### 3. 확정 급소 데이터 전달

트릭플라워 한 건을 엔진에 하드코딩하지 않는다. 원본 기술 데이터의 `willCrit`을 공통 경로로
전달한다.

#### 빌드

`build.mjs`의 최종 기술 객체에 `m.willCrit`을 보존한다. `move-mechanics.json`의 오버라이드도
필요할 경우 같은 필드를 덮어쓸 수 있도록 기존 `mechanicFlags` 병합 순서를 확인한다.

#### 엔진

급소 판정의 입력을 다음 세 종류의 OR 조건으로 만든다.

```text
기술의 willCrit
수동 기술 슬롯 급소 설정
특성에 의한 조건부 급소
```

이후 기존 방어측 급소 차단 판정을 그대로 통과시킨다. 따라서 전투무장과 조가비갑옷은 확정 급소도
차단하며, 틀깨기로 해당 방어 특성이 무시되면 급소가 적용된다.

확정 급소는 기존 엔진의 다음 동작을 그대로 사용해야 한다.

- 급소 대미지 1.5배
- 공격측 음수 랭크 무시
- 방어측 양수 랭크 무시
- 리플렉터 및 빛의장막 무시
- 스나이퍼 추가 배율
- 수류연타의 각 타격에 급소 적용

`validate-data.mjs`에는 원본 기술이 `willCrit: true`일 때 생성 기술 데이터에도 해당 값이
보존되었는지 검증을 추가한다.

### 4. 기술별 수동 급소 설정

메인 필드 패널의 전역 급소 체크박스를 제거하고 공격측 기술 행마다 급소 설정을 둔다.

사이드 상태 예시:

```js
moveCriticalOverrides: [false, false, false, false]
```

#### 슬롯 동작

- 일반 기술: 사용자가 급소를 켜거나 끌 수 있음
- `willCrit` 기술: 체크된 상태로 표시하며 비활성화
- 빈 슬롯: 체크박스 비활성화
- 기술 변경: 해당 슬롯의 수동 급소 값을 `false`로 초기화
- 포켓몬 변경: 기술과 함께 네 슬롯 모두 초기화
- 프리셋 적용: 저장 기술을 적용한 뒤 수동 급소 네 슬롯 초기화
- 공수교대: 사이드 객체와 함께 급소 배열도 이동
- 같은 포켓몬 재선택으로 기술이 유지되는 경로: 기존 슬롯 설정도 유지

메인 계산 시 기술별 필드 복사본을 만들어 엔진에 전달한다.

```js
const moveField = {
  ...calcField,
  isCritical: !!calcAtk.moveCriticalOverrides?.[i],
};
```

엔진은 별도로 `move.willCrit`을 판정한다. UI 상태에서 확정 급소를 억지로 수동값으로 저장하지
않는다.

#### UI 구조

공유 `renderToolMoveList()`의 기본 열 구성은 바꾸지 않는다. 메인 계산기만 명시적으로 급소 열을
추가하여 역계산과 세부조정의 기존 레이아웃을 보호한다.

예시:

```js
columns: ['index', 'name', 'type', 'power', 'critical', 'readout']
```

`renderToolMoveList()`는 알 수 없는 열에 대해 `row[column]`을 반환할 수 있으므로 계산기 행에
`critical` HTML을 제공하고 계산기 전용 CSS 그리드 폭만 추가하는 접근이 가능하다.

모바일에서는 약 40px의 고정 급소 열을 추가하되 텍스트 겹침과 불필요한 가로 스크롤을 실제
렌더링으로 확인한다.

메인 계산기에서 제거하는 항목:

- `src/calc-template.html`의 `#critHit`
- `src/js/03-60-calc-events.js`의 전역 급소 이벤트
- `syncFieldControls()`의 `#critHit` 동기화

공통 엔진의 `field.isCritical` 입력 계약은 유지한다. 역계산은 관측한 단일 기술의 급소 여부를
입력하므로 기존 급소 UI를 그대로 둔다. 세부조정은 `willCrit` 자동 판정만 공유한다.

## 구현 순서

전체 변경을 한 번에 섞지 말고 아래 순서로 구현하고 각 단계에서 테스트한다.

### 1단계: 데이터 및 공통 엔진

- `willCrit` 빌드 보존
- 엔진 급소 판정 확장
- 데이터 검증 추가
- 트릭플라워 및 상호작용 골든 테스트 추가

이 단계는 UI와 자동 진입 상태를 건드리지 않는다.

### 2단계: 메인 계산기 기술별 급소

- 사이드 상태 배열 추가
- 기술 행 급소 열 추가
- 전역 급소 UI 제거
- 기술별 필드 복사본 사용
- 포켓몬, 기술, 프리셋, 초기화, 공수교대 상태 처리
- 구조 및 모바일 UI 검증

### 3단계: 자동 진입 효과 정리

- 날씨 및 필드 owner/base 상태 추가
- 선택 이벤트 기반 필드 적용과 복원
- 랭크 효과와 재앙 효과 함수 분리
- 프리셋, 도감, 폼, 자동 토글, 공수교대, 초기화 경로 연결
- 기존 `lastAutoEntry` 및 수동 오버라이드 중 불필요해진 부분 제거

각 단계가 통과한 뒤 다음 단계로 진행하면 회귀 원인을 쉽게 특정할 수 있다.

## 필수 테스트 경우의 수

### 자동 필드 효과

- 공격측 가뭄 후 방어측 잔비: 비
- 방어측 잔비 후 공격측 모래날림: 모래바람
- 비소유자 교체: 현재 날씨 유지
- 소유자 교체, 반대편 날씨 특성 존재: 반대편 날씨로 복원
- 소유자 교체, 반대편 효과 없음: base로 복원
- 양쪽이 같은 날씨: 마지막 선택칸으로 owner 갱신
- 수동 날씨 후 자동 날씨 선택: 자동 날씨
- 자동 날씨 후 수동 날씨 선택: 수동 날씨 및 owner 해제
- 자동 효과 OFF/ON
- OFF 상태에서 포켓몬 또는 특성 변경 후 ON
- 공수교대 후 owner와 제거 동작
- 전체 초기화
- 프리셋의 저장 특성이 기본 특성과 다른 경우
- 폼 변경으로 특성이 변경 또는 유지되는 경우
- 날씨와 필드 각각 동일한 전이 테스트

### 랭크 및 재앙 효과

- 위협 적용 후 특성 제거: 수동 랭크 복원
- 양쪽 위협
- 위협 차단 특성
- 수동 랭크와 위협의 합산
- 자기 랭크 상승의 재계산 비누적
- 다운로드의 방어/특방 비교
- 재앙 특성 적용과 제거
- 수동 재앙 체크 해제 및 자동 효과 OFF

### 확정 및 수동 급소

- 트릭플라워가 수동 체크 없이 급소
- 일반 기술은 수동 체크 없으면 비급소
- 네 슬롯의 수동 급소 설정이 서로 독립
- 기술 변경 시 해당 슬롯만 초기화
- 포켓몬 변경 시 전체 초기화
- 프리셋 적용 시 전체 초기화
- 공수교대 시 사이드와 함께 이동
- 조가비갑옷 및 전투무장의 확정 급소 차단
- 틀깨기와 급소 차단 특성
- 스나이퍼 추가 배율
- 급소의 리플렉터 무시
- 음수 공격 랭크와 양수 방어 랭크 무시
- 수류연타 다단 급소
- 수동 급소와 `willCrit` 중복 시 1회만 적용

## 비대상

이번 리팩터링에서 다음 항목은 함께 수정하지 않는다.

- 모래뿜기를 피격 발동으로 변경
- 초상투영의 테라스탈 조건 추가
- 불요의검 및 불굴의방패의 배틀당 1회 상태 추적
- 델타스트림 및 새로운 날씨 상태 추가
- 일반 고급 급소율(`critRatio`)의 확률 계산
- 럭키챈트 상태 모델
- 역계산 또는 세부조정의 UI 재설계
- 대미지 공식 단계의 광범위한 재작성

## 완료 조건

- 마지막으로 조작한 날씨/필드 특성이 최종값을 결정한다.
- 소유자 제거 시 반대편 효과 또는 수동 base가 정확히 복원된다.
- 위협과 자기 랭크 효과가 재계산으로 누적되지 않는다.
- 트릭플라워 등 `willCrit` 기술이 공통 엔진에서 자동 급소로 계산된다.
- 메인 계산기의 수동 급소 설정이 기술 슬롯별로 독립적이다.
- 확정 급소와 수동 급소 모두 기존 차단 특성 및 급소 보정과 올바르게 상호작용한다.
- 역계산과 세부조정의 기존 계약이 유지된다.
- 전체 `npm.cmd test`가 통과한다.
- 생성 HTML과 Pages 빌드가 최신 소스에서 재생성된다.
- 작업 트리에 의도하지 않은 데이터 또는 문서 변경이 없다.
