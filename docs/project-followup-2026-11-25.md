# 샘플 계산기 후속 개선과 실제 브라우저 검증

2026년 11월 25일. 비교 기준은 같은 날 앞서 전달한 [프로젝트 재검토판](project-completion-review-2026-11-25.md)이다. 두 버전은 동일한 규정 데이터와 샘플을 사용했다. 이번 작업은 로컬 작업 사본과 후보 산출물에 반영했다.

## 판정과 변경

| 사용자 동작 | 수정과 확인 결과 |
|---|---|
| 키보드로 파티 샘플 불러오기 | 공격측 패널을 다시 그리면 불러오기 버튼의 기존 DOM 요소가 사라져 포커스가 본문으로 갔다. 선택창을 연 버튼의 용도로 새 버튼을 찾아 포커스를 돌리고, 창을 여닫을 때 예약된 포커스 이동이 다음 입력을 가로채지 않도록 했다. 실제 Chrome에서 Enter로 한카리아스를 불러온 뒤 공격측 불러오기 버튼에 포커스가 돌아왔다. 저장 슬롯 교체는 취소가 기본 포커스이고, Esc로 두 단계를 닫으면 원래 저장 버튼으로 돌아왔다. |
| 두 탭에서 파티 수정 | 같은 출처의 별도 탭 두 개에서 슬롯 상세를 펼쳐 HP 포인트를 편집했다. 서로 다른 슬롯은 두 값이 모두 저장됐다. 같은 슬롯을 바꾸면 한 창에 확인창이 뜨고 취소하면 먼저 저장한 값이 두 창에 남았다. 네이티브 Web Locks와 Web Locks를 제외한 실제 IndexedDB 트랜잭션 경로에서 각각 재현했다. 이 시나리오를 공개 번들용 브라우저 회귀에 추가했다. |
| 파티 내보내기 | UI로 받은 JSON을 다시 파싱해 10파티 × 6슬롯과 테스트 파티의 한카리아스·몰드류를 확인했다. 이미지 버튼으로 받은 파일은 디코딩 가능한 2400 × 1600 PNG였다. |
| 계산기·세부조정·역계산 간 이동 | 탭 전환이 최신 요청인지 확인한 뒤 샘플을 적용하고 화면을 한 번 그린다. 파티에서 배치를 받을 때 세부조정·역계산·상성표는 각자 자기 상태를 갱신한다. 파티 코드가 다른 메뉴의 내부 상태를 직접 쓰던 경로를 정리했다. 공개·단독 HTML을 각각 320·375·1280px에서 실행해 불러오기, 반대편에 적용, 상성표 멤버, 선택창 너비와 포커스 복귀를 확인했다. |
| 역계산 반복 사용 | 새 관측에서 대기 중인 Worker를 재사용한다. 진행 중인 작업을 취소하면 기존 Worker가 종료되고, 그 Worker에서 뒤늦게 온 이벤트가 다음 요청을 중단시키지 않는다. 메뉴를 여는 즉시 Worker를 만드는 방안은 시범 측정에서 일관된 이득을 확인하지 못해 최종본은 분석을 요청할 때 생성한다. |

## 구조와 초기 로딩

- 탐색 코드에서 앱 초기화 모듈로 역참조하던 경로를 제거하고, 선택창 식별자는 선택창 모듈이 관리한다. `src`의 50개 JS 모듈에서 정적 의존 연결은 **275 → 270개**, 서로 순환 참조하는 최대 그룹은 **18 → 12개**가 됐다. 남은 12개는 계산 상태·입력·렌더링에 모여 있다.
- 파티 이미지 코드는 내보내기 버튼을 누를 때 로드한다. 공개용 JS에서 불필요한 공백을 제거하고 HTML 헤드에서 초기 게임 데이터와 앱 모듈의 다운로드를 시작하도록 했다. 최초 계산기에 도감·세부조정·역계산·상성표와 파티 이미지 코드를 미리 싣지 않는지 검사한다.
- Pages의 초기 gzip 자산 합계는 **263,122 → 254,689바이트**로 8,433바이트 줄었다. 정적 파일 분할로 초기 자산 수는 **5 → 7개**가 됐다. 전체 자산은 **379,342 → 367,486바이트**다. 이는 생성 파일의 gzip 합계이며 HTML, 응답 헤더, 외부 스프라이트와 CDN 실전 전송량은 포함하지 않는다.

## 브라우저 성능 실측

Chrome 156의 같은 로컬 미리보기에서 기준판과 수정판을 번갈아 실행했다. 각 폭·버전에서 새 문서를 5회씩 열었다. 데이터 준비 및 계산 결과가 DOM에 나타난 시점을 측정했다. 표는 중앙값(ms)이며 하드웨어 모바일 기기, 네트워크 제한, 캐시 강제 삭제 조건은 사용하지 않았다.

| 화면 폭 | 초기 계산 카드 준비 전 → 후 | 문포스 옵션 선택 → 피해 표시 전 → 후 | 첫 형태 분석 클릭 → 후보 표시 전 → 후 |
|---|---:|---:|---:|
| 320px | 186 → 204 | 19 → 23 | 1,558 → 1,240 |
| 375px | 206 → 155 | 19 → 16 | 1,325 → 1,678 |
| 1280px | 180 → 176 | 16 → 13 | 1,698 → 1,251 |

총 30회 모두 누리레느의 문포스 → 브리두라스가 **93–109 HP**, 상대 잔여 HP 35%로 역계산한 결과는 **화면에 표시되는 대표 후보 카드 5개**였다. 기록된 계산기·역계산 화면에는 문서 너비를 벗어나는 수평 오버플로가 없었다. 375px의 수정판 첫 역계산은 963–2,632ms, 기준판은 906–1,576ms로 편차가 컸다. 전송량 감소는 재현되지만 모든 화면에서 응답 시간이 단축된다고 결론 내리기는 어렵다. 이 사례에서 데이터 형식이나 대미지 공식을 더 나눌 근거는 부족하다.

## 검증 범위와 운영 상태

- 기능 회귀는 `npm test`, 참조 전투 대조는 고정 Showdown `f1040ecb5f5dba252e0e351e392dc409a5089ace`로 실행했다. 피해·속도 3,039개 시나리오와 48,624개 난수, 독립 KO 분포 135개, KO 조건 76개와 19,456전 대조를 통과했다. 별도 참조 묶음도 592전·기술 536개를 통과했다.
- 공개 HTML은 외부 Worker, 단독 HTML은 내장 코드로 만든 Blob Worker에서 형태 역계산을 실행했다. 브라우저의 URL 정책이 직접 여는 파일 경로를 차단해, 단독 HTML은 로컬 HTTP에서 검증했다. 모바일 폭은 실제 Chrome 레이아웃으로 확인했고 iOS Safari·Android 실기기의 터치·파일 열기·저사양 성능은 미확인이다.
- 기본 공개 후보인 `pages/`의 광고 레일은 0개, 별도 `public/` 후보는 좌·우 각 1개다. 계산 정책과 데이터 원본은 이전 검토 기준을 유지한다. 실제 광고 연결, GitHub 푸시, 운영 게시 전환은 수행하지 않았다.
